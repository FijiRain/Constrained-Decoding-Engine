# Call Me Maybe

## Description

Call Me Maybe is a function calling agent built on top of a small language model (Qwen3-0.6B). Given a natural language prompt and a set of function definitions, the program determines which function to call and extracts the correct arguments with the correct types, outputting a structured JSON file.

The core challenge of this project is **constrained decoding**: rather than prompting the model and hoping for valid JSON output, the program intervenes at each token generation step to guarantee that the output conforms to a given schema. This is achieved by masking invalid tokens in the logit distribution before sampling, forcing the model to only generate tokens that are structurally valid at each position.

## Example Usage

Given the following input prompt file:

```json
[
  { "prompt": "What is the sum of 2 and 3?" },
  { "prompt": "Greet shrek" }
]
```

And the following function definitions:

```json
[
  {
    "name": "fn_add_numbers",
    "description": "Add two numbers together and return their sum.",
    "parameters": {
      "a": { "type": "number" },
      "b": { "type": "number" }
    },
    "returns": { "type": "number" }
  },
  {
    "name": "fn_greet",
    "description": "Generate a greeting message for a person by name.",
    "parameters": {
      "name": { "type": "string" }
    },
    "returns": { "type": "string" }
  }
]
```

The program produces:

```json
[
  {
    "prompt": "What is the sum of 2 and 3?",
    "name": "fn_add_numbers",
    "parameters": { "a": 2.0, "b": 3.0 }
  },
  {
    "prompt": "Greet shrek",
    "name": "fn_greet",
    "parameters": { "name": "shrek" }
  }
]
```

## Algorithm Explanation

The constrained decoding pipeline operates in three phases for each prompt:

**1. Function name selection (`enforce_name`)**

All available function names are pre-encoded into token sequences. At each generation step, only the tokens that continue a valid function name are allowed. The logits of all other tokens are set to `-inf` before applying `argmax`, making it impossible for the model to generate an invalid function name. Generation stops when a complete function name has been produced.

**2. Parameter key generation**

Parameter names are known in advance from the function definition and are hardcoded directly into the JSON template, rather than generated by the model. This guarantees correct key names without any model inference.

**3. Parameter value generation (`enforce_params`)**

For each parameter, the allowed tokens depend on the parameter type:

- `number`: Only digit characters (`0-9`), `.`, and `-` are allowed. Generation stops when the model's top token is not a numeric character. The resulting token sequence is decoded and cast to `float` to ensure decimal formatting.
- `string`: The model generates freely until a token containing a closing quotation mark is produced. The quotation mark and any subsequent structural characters (e.g. `}`) are stripped from the value.

Between each phase, the full generation history is passed back to the model as context, ensuring coherent next-token prediction.

## Design Decisions

**Pydantic for data validation**: All input JSON files are parsed into Pydantic models (`Function`, `Parameters`, `Prompt`). This provides automatic type validation and clean attribute access throughout the codebase.

**Separation of concerns**: Parsing logic (`JSON_parsing.py`), LLM interaction and constrained decoding (`LLM_run.py`), and the entry point (`__main__.py`) are kept in separate modules. Each function has a single, well-defined responsibility.

**Pre-prompt for semantic guidance**: A system prompt is prepended to each generation context to guide the model toward function calling behaviour, listing all available functions and their descriptions. This improves the model's semantic understanding even though structural correctness is enforced independently.

**Hardcoded JSON structure**: The JSON skeleton (`{"prompt": ..., "name": ..., "parameters": {`) is built programmatically rather than generated by the model. Only the values that require model inference (function name, parameter values) are generated token by token.

**Context accumulation**: The full token history is passed to `get_logits_from_input_ids` at each step, ensuring the model always has complete context when predicting the next token.

## Performance Analysis

**Accuracy**: Function name selection is deterministic and always produces a valid function name from the available set. Numeric parameter extraction is reliable for simple arithmetic prompts. String parameter extraction works well for proper nouns and simple values. Semantic accuracy (e.g. generating correct regex patterns) is limited by the small size of the underlying model (Qwen3-0.6B).

**Speed**: Each prompt requires multiple sequential LLM calls (one per token generated), which makes generation relatively slow. The model is instantiated once and reused across all prompts to avoid repeated initialisation overhead.

**Reliability**: The constrained decoding guarantees that the output JSON is always structurally valid, regardless of the model's behaviour. Invalid or unexpected model outputs cannot corrupt the output schema.

## Challenges Faced

**Token boundary mismatches**: Closing characters such as `"` or `}` are often fused into a single token by the BPE tokenizer (e.g. `"}` as one token). This required decoding each generated token and checking whether it *contains* a quote, rather than comparing token IDs directly.

**Context ordering**: When generating multiple parameters, the accumulated token history (`context`) must be updated correctly after each parameter to reflect the full generation so far. An early bug caused the second parameter's key to appear before the first parameter's value in the context, leading to incoherent generation.

**Numeric formatting**: The model sometimes generates integers (`2`) when floats (`2.0`) are expected. This was resolved by decoding the numeric token sequence and casting it through `float()` before storing the result.

**LLM semantic limitations**: The Qwen3-0.6B model occasionally produces semantically incorrect values for complex string parameters (e.g. regex patterns). This is an inherent limitation of the model size and cannot be addressed through constrained decoding alone, which only controls format, not meaning.

## Testing Strategy

The program was validated against both the provided sample inputs and the private test set from the 42 moulinette. Each output JSON was inspected manually to verify:

- Correct function name selection for each prompt
- Correct parameter names matching the function definition
- Correct types (`float` for numbers, `str` for strings)
- Valid JSON structure throughout the output file

Edge cases tested include prompts with multiple parameters, string parameters containing spaces, and functions with a single parameter.
